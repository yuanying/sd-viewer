# sd-viewer 設計

## 目的

Stable Diffusion WebUI (AUTOMATIC1111 / Forge) が出力した画像群を、生成パラメータで検索・閲覧できるようにする。出力ディレクトリは日々増え続け、既存のファイルマネージャでは「どのモデルで、どの LoRA を使って、どんなタグで生成したか」を横断的に探せない。ここを解決する。

## 全体構成

単一の Go バイナリがローカルで HTTP サーバとして動作し、ブラウザから利用する。

```
                    ┌──────────────── sd-viewer (単一バイナリ) ───────────────┐
出力ディレクトリ ──▶ │  watcher ─▶ scanner ─▶ metadata ─▶ index (SQLite/FTS5) │
  (監視対象)         │                     └▶ thumb (キャッシュ生成)          │
                    │                                    ▲                   │
                    │                          server (HTTP API) ◀─ webui    │
                    └────────────────────────────────────┬───────────────────┘
                                                         ▼
                                                    ブラウザ (React)
```

### パッケージ責務

| パッケージ | 責務 |
| --- | --- |
| `internal/metadata` | PNG のテキストチャンクを読み、A1111 形式の生成パラメータを構造体へ変換する |
| `internal/index` | SQLite への永続化。画像レコードの登録・更新・削除、検索、ファセット集計、タグ補完 |
| `internal/scanner` | ディレクトリの初回走査と、ファイルイベントの受け取り。インデックスとの差分同期 |
| `internal/thumb` | サムネイルの生成とキャッシュ管理 |
| `internal/server` | HTTP API と静的アセット配信 |
| `web` | React + TypeScript の SPA |

## メタデータ解析

### 入力形式

WebUI は PNG のテキストチャンク（`tEXt`、まれに `iTXt`）に `parameters` というキーで生成情報を書き込む。内容は次の 3 ブロックからなる。

1. **positive prompt** — 先頭から `Negative prompt:` 行の直前まで（複数行を含む）
2. **negative prompt** — `Negative prompt:` 以降、パラメータ行の直前まで（省略されることがある）
3. **パラメータ行** — 最終行。`キー: 値` をカンマ区切りで並べたもの

パラメータ行の値にカンマが含まれる場合は `Lora hashes: "a: h1, b: h2"` のようにダブルクォートで囲まれるため、クォート内のカンマでは分割しない。

### 抽出する情報

`Steps` / `Sampler` / `Schedule type` / `CFG scale` / `Seed` / `Size` / `Model` / `Model hash` / `Denoising strength` / `Version` などの既知キーは型付きフィールドへ格納する。それ以外のキー（`Module 1`、`Beta schedule alpha`、拡張機能が追加するキーなど）は失わずに「その他パラメータ」として保持し、詳細表示で参照できるようにする。

LoRA は 2 系統から収集して統合する。

- プロンプト中の `<lora:名前:重み>` 記法 — 重みが取れる
- パラメータ行の `Lora hashes` — ハッシュが取れる。プロンプトに記法がない場合（拡張機能経由の適用など）でも記録される

タグはプロンプトをカンマで分割し、前後の空白と強調記法の括弧・重み指定を取り除いて正規化したものとする。`<lora:...>` は LoRA として扱いタグからは除く。

### 解析できない場合

`parameters` チャンクを持たない画像（手動で置いたファイル、グリッド画像など）もインデックスには登録する。パラメータ不明として一覧に出し、パス・サイズ・更新日時での絞り込みは効くようにする。

## インデックス

SQLite を単一ファイルで持つ。FTS5 が必要なため、cgo 不要で FTS5 を含む `modernc.org/sqlite` を使う。

### テーブル構成

| テーブル | 内容 |
| --- | --- |
| `images` | 画像 1 枚 1 行。パス、ルート ID、サイズ、更新日時、幅・高さ、生成日時、prompt、negative prompt、既知パラメータ、その他パラメータ(JSON) |
| `image_loras` | 画像と LoRA の対応。LoRA 名、重み、ハッシュ |
| `image_tags` | 画像とタグの対応。タグ名、positive / negative の別 |
| `images_fts` | FTS5 仮想テーブル。prompt と negative prompt を対象に全文検索 |

パスに UNIQUE 制約を置き、再スキャン時は更新日時とサイズが一致すれば解析をスキップする。ファイル移動は「削除 + 作成」として届くことがあるため、内容ハッシュではなくパスを主キーとし、移動イベントでは行のパスを更新する。

### 検索

クエリは次の要素の AND で構成される。

- **全文検索** — prompt / negative prompt に対する FTS5 マッチ
- **ファセット** — モデル、LoRA、Sampler、解像度、ルート、フォルダ。同一ファセット内の複数選択は OR、ファセット間は AND
- **日付範囲** — 生成日時（メタデータがなければファイル更新日時）
- **並び順** — 生成日時の新しい順を既定とし、古い順・ファイル名順を選べる

ファセットの候補と件数は、現在の絞り込み条件を適用した結果に対して集計する。

## ファイル監視

`fsnotify` で監視対象ディレクトリを再帰的に watch する。WebUI は日付ごとにサブディレクトリを作るため、新規ディレクトリの作成を検知したら watch 対象へ追加する。

書き込み途中のファイルを読むと解析に失敗するため、イベントは一定時間まとめてから処理する。同一パスへのイベントが続く間は処理を遅延させ、静まってから解析する。

起動時は必ずフルスキャンを行い、停止中に起きた変更を回収する。インデックスにあって実ファイルが存在しない行は削除する。

## サムネイル

スキャン時にキャッシュディレクトリへ JPEG で事前生成する。ファイル名は画像 ID から決め、サブディレクトリへ分散させる。ID を使うため、画像を移動してもサムネイルは作り直さずに済む。

サムネイルの更新日時には元画像の更新日時を写す。両者が一致していれば最新とみなし、食い違っていれば作り直す。書き出しは一時ファイル経由で行い、途中で終了しても壊れたサムネイルを残さない。生成はスキャンの並列度に従い、UI の初回表示を待たせない。

## HTTP API

| メソッド / パス | 内容 |
| --- | --- |
| `GET /api/images` | 検索・絞り込み・ページング付きの画像一覧 |
| `GET /api/images/{id}` | 画像 1 枚の全メタデータ |
| `GET /api/facets` | 現在の絞り込み条件下でのファセット候補と件数 |
| `GET /api/tags` | タグ補完候補（前方一致・出現頻度順） |
| `GET /api/thumb/{id}` | サムネイル画像 |
| `GET /api/raw/{id}` | 原画像 |
| `GET /api/status` | スキャン進捗とインデックス統計 |
| `GET /api/events` | 同じ内容を Server-Sent Events で流し続ける |

絞り込み条件はクエリ文字列で渡す。`model` や `tag` のように同名のパラメータを複数指定でき、同名どうしは OR、異なる項目どうしは AND として扱う。解釈できない値は指定がなかったものとみなし、エラーにはしない。

画面側のルーティングを壊さないよう、`/api/` 以外の見つからないパスには `index.html` を返す。

## フロントエンド

Vite + React + TypeScript。ビルド成果物を `go:embed` でバイナリへ埋め込む。開発時は Vite dev server から API サーバへプロキシする。

画面は左にファセットサイドバー、上部に検索ボックス、中央に画像グリッドを置く。グリッドは仮想スクロールで数万件を扱う。画像をクリックすると詳細を表示し、prompt や各パラメータをコピーできる。詳細から「同じモデル」「同じ LoRA」「このタグ」へ 1 クリックで絞り込める。

## テスト方針

Go 標準の `testing` を用い、テスト名を振る舞いで表す（`Test<対象>_<期待する振る舞い>`）。各テストは Given / When / Then の 3 段構成で書く。

- `metadata` — 実出力から採取したサンプル文字列を testdata に置き、期待する構造体と突き合わせる。異常系（チャンクなし、パラメータ行なし、クォート内カンマ）を網羅する
- `index` — 一時ファイル DB に対して、登録・更新・削除・検索・ファセット集計を検証する
- `scanner` — 一時ディレクトリへファイルを作成・移動・削除し、インデックスが追従することを検証する
- `server` — `httptest` で API のリクエストとレスポンスを検証する

実装前にテストを書き、失敗を確認してから実装する。
